# AGENTS: What makes a good release / deployable artifact

> **Copy this file** into any project to guide AI agents on release quality.
> Companion: `AGENTS-record-release.md` (how to record the release in app-track).

## Purpose

A “release” is not “code that compiled once.” It is a **reproducible, attributable, inspectable** unit that operators can deploy and auditors can trust. app-track stores the **metadata + evidence**; registries/SCM remain the homes of bytes and source.

## Definition: good deployable artifact

A deployable artifact is good when **all** of the following hold:

1. **Content-addressed** — Identified by an immutable digest (`sha256:…`), not only a mutable tag like `:latest`.
2. **Locatable** — Has a stable URI where that digest can be fetched (OCI, HTTPS, package registry, etc.).
3. **Tied to source** — Linked to an exact SCM commit (and preferably a version tag).
4. **Inventoried** — Accompanied by a machine-readable SBOM (CycloneDX JSON preferred) that lists components.
5. **Attributable** — Produced by an authenticated publisher identity; in app-track, wrapped in a verified envelope.
6. **Minimal privilege** — Built and published with credentials scoped to that application only.
7. **No secret payload** — Does not embed credentials, private keys, or production secrets.

If any of 1–5 are missing, **do not** call it a production-ready release; fix the gap or label it a snapshot/dev build.

## Artifact roles

| Role | Meaning |
|------|---------|
| `DEPLOYABLE` | What actually runs or is installed (image, binary, package). Prefer ≥1 per release. |
| `SUPPORTING` | Needed to deploy/operate but not the primary runtime (config pack, DB schema bundle). |

SBOMs, signatures, and attestations are **evidence**, not artifact rows — unless you also publish them as downloadable supporting artifacts with their own digest+URI.

## Digest & URI discipline

**Do:**

- Compute digest from the **exact bytes** that will be deployed.
- Prefer URI forms that embed the digest (e.g. `oci://…@sha256:…`, `https://…/file-sha256-….tgz`).
- Keep digest algorithm explicit: `sha256:<lowercase-hex>`.

**Don’t:**

- Record only `image:tag` without digest.
- Point URI at a moving channel (`latest`, `main`, floating branch).
- Claim a digest you did not compute from the artifact you built.

## Source linkage

Minimum:

- `scm_uri` — clone URL or canonical repo URI  
- `commit_sha` — full git object id of the tree that produced the build  

Recommended:

- Annotated version tag matching `version`  
- CI run URL in annotations (optional)  
- Match tag ↔ version ↔ changelog entry  

## SBOM quality bar

A good SBOM for recording:

- CycloneDX JSON (1.4+), UTF-8  
- Includes components with **purl** and/or **name+version** whenever available  
- Reflects the **shipped** artifact (not an unrelated workspace)  
- Generated by a known tool (Syft, Trivy, cargo-cyclonedx, etc.) — record tool in CI logs  

Empty or unparseable SBOMs are **not** acceptable for a trusted publish.

## Optional but stronger (when available)

- Cosign / Sigstore signature or attestation on the deployable (app-track verifies when attached)
- Separate config and DB schema artifacts with their own digests
- CI metadata overlay only for facts the SBOM cannot express

## Versioning

- Prefer SemVer-like strings (`1.2.3`, `1.2.3-rc.1`) consistent with tags.
- Never reuse a version for different content; app-track rejects duplicate versions for an app.
- Use a new `idempotency_key` for a new attempt with different content; reuse the same key only for exact retries.

## Anti-patterns (reject / rewrite)

| Anti-pattern | Why it fails |
|--------------|--------------|
| “Release” = git push to main | No digest, no SBOM, no deployable URI |
| Tag-only image reference | Tag can be moved; not content-addressed |
| SBOM omitted “to save time” | Inventory and trust queries become impossible |
| Secrets in artifact or evidence | Security incident; rebuild without secrets |
| One mega-zip of unrelated apps | Unclear ownership; split by application |
| Publishing without Publisher binding | Authz failure; fix RBAC first |

## Checklist before you call `app-track-agent publish`

- [ ] At least one `DEPLOYABLE` with `sha256:…` digest and immutable URI  
- [ ] `source.scm_uri` + `commit_sha` match the build  
- [ ] CycloneDX SBOM file exists and parses  
- [ ] Version is new for this application  
- [ ] Manifest validates (`app-track-agent validate-manifest`)  
- [ ] No secrets in artifact, SBOM, or manifest  

If every box is checked, record the release. If not, fix the release — do not “publish anyway.”
